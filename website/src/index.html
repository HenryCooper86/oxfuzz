Engine CLI or oxfuzz?

The same engines.
A connected workflow around them.

Direct engine use gives you close control over flags and scripts. oxfuzz brings target selection, harness review, campaign controls and retained evidence into one place.

Workflow comparison — not a throughput benchmark
Task Using engines directly Using oxfuzz
Choose what to fuzz Engine CLIIdentify a target using your code knowledge and analysis tools. oxfuzzInspect ranked candidates and explained AI recommendations before selecting a target.
Prepare a harness Engine CLIWrite or adapt a target and configure its instrumented build. oxfuzzGenerate, compile and smoke-test a harness; review and approve the exact revision.
Run and monitor Engine CLIUse engine options, terminal output and native monitoring tools. oxfuzzSet time, CPU and memory limits, follow supported engine metrics, and stop from the workbench.
Investigate crashes Engine CLIUse the engine's crash output and reproduction or minimization tools, alongside your debugger. oxfuzzScan retained crashes, inspect grouped findings and request a separate AI report for review.
Repeat and keep context Engine CLIOrganize corpus/output directories and connect your own scheduling and reporting scripts. oxfuzzKeep run history, harness revisions and policy decisions together; schedule approved targets with explicit authorization.

What the GUI adds: coordination, model assistance and reviewable evidence. Engines already provide fuzzing, corpus handling and monitoring features; for example, AFL++ includes status and plotting tools, and syzkaller has its own web statistics.

What still matters: target quality, harness correctness, corpus, engine settings and hardware. oxfuzz requires Docker and provider access for AI features; syzkaller still needs a compatible kernel and VM setup. No speedup or higher bug yield is claimed here.

BEFORE YOUR FIRST CAMPAIGN

Desktop app.
Isolated engines.

Install Docker and keep its daemon running. The sandbox kit builds the pinned engine toolchain locally; it does not include the application source.

1

Install the desktop app

Open the package for your system. On macOS, move oxfuzz to Applications. On Linux, install the DEB/RPM or make the AppImage executable. On Windows, run the installer.

2

Build the sandbox

Download and extract the sandbox kit. Run these commands from its directory using Bash, Python 3 and Docker. Windows users need a WSL 2 shell with Docker integration. The first build downloads toolchains and needs several GB of disk space. 

tar -xzf oxfuzz-sandbox-kit-{{VERSION}}.tar.gz
cd oxfuzz-sandbox-kit-{{VERSION}}
./scripts/build-sandbox.sh

Keep the resulting image tag oxfuzz/fuzz-sandbox:0.2.2. The desktop app uses this local image.

3

Connect a provider and open a project

Configure your chosen AI provider in Settings. Provider access is required for AI assistance and normal harness review. Confirm sandbox readiness, discover a target, and review the harness before approving execution.

Kernel fuzzing with syzkaller also needs a compatible instrumented kernel, root filesystem and guest SSH key. These are not included in the desktop download. Physical automotive testing requires separate setup and approval.

VERIFY YOUR DOWNLOAD

Check the bytes.

Compare the SHA-256 of your download with the published checksums before installing. 

# macOS
shasum -a 256 your-download.dmg
# Linux
sha256sum your-download.AppImage
# Windows PowerShell
Get-FileHash .\your-download.msi -Algorithm SHA256

Checksums detect incomplete or altered files. They are not a substitute for a trusted publisher signature.
