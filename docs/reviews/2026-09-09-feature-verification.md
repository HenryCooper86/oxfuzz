# Feature-by-feature verification for daily fuzzing work

Date: 2026-09-09. Baseline: `7a4af3645439dc3efd9c94011587165424a1616c`.

## Assessment and scope

oxfuzz has a broad implemented workbench, but the evidence does not establish best-in-class daily operation. Passing software tests, available engine binaries, and a successful project build are different claims from effective real-project fuzzing. This review inventories the shipped capability families, inspects selected implementations and tests, runs fresh checks, and records practical acceptance criteria. It is not an exhaustive line-by-line security review, a certification of every control, or a completed competitive benchmark.

The earlier [daily-work review](2026-09-07-fuzzing-engineer-daily-work.md) and [delivery evidence](2026-09-08-phase-delivery-evidence.md) remain historical evidence. Their results are not counted as fresh results here.

## Reproduced problems and concrete limitations

1. **Frontend dependency gate failed.** A clean install followed by the canonical audit stopped at Vitest 4.1.10 and its mocker dependency, reporting two moderate findings for one underlying advisory. Updated the direct dependency and lockfile to the patched 4.1.11 release. This is development-tool exposure; no production exploitability is inferred. [Upstream advisory](https://github.com/advisories/GHSA-82fw-gwwq-j7x9).
2. **Release blocker: the demo approves a different generation from the one preceding the prompt (resolved in milestone 1).** `scripts/demo-cve-rediscovery.sh` first invokes `harness --repair 3`, prompts, then invokes `harness --promote`. `cmd_harness` creates another draft for that second invocation. A stub CLI execution reproduced the exact command sequence without executing target code. The real CLI's own `promotion_required_message` explicitly warns against this sequence. The advertised review pause therefore does not approve the exact preceding source. Remediation must use a retained attempt ID and prove that no generation occurs after approval. Do not solve this by automatically approving the second generation.
3. **The demo preflight overstates readiness (resolved in milestone 1).** It labels `doctor` as checking the provider and says a passing check means the full demo can run. `SystemStatus::fuzzing_ready` checks Docker, an image, and any supported engine; it does not establish a configured working provider or readiness of the requested engine. In particular, a machine with only one other engine can pass. Required acceptance: absent provider and absent selected engine must produce named preflight failures before authoring.
4. **Historical replay is a new campaign with a fixed seed.** `ServiceContainer::replay_run` resolves the current promoted harness, current canonical corpus, and current resource policy. It preserves original engine/duration when allowed and links the new run. Additionally, the honggfuzz adapter does not accept a deterministic RNG seed; a recorded seed is provenance, not control of that engine's randomness. This is documented intentional behavior, not exact historical reproduction. An engineer needs a separate immutable-input rerun workflow for controlled investigations, or very explicit labels wherever replay is offered.
5. **Coverage experiments cannot establish target-function entry.** The design and response explicitly report `no_exact_run_scoped_function_coverage`. Aggregate edge deltas cannot show that an improved harness reached the intended parser. This limits the central coverage-investigation workflow even when every existing comparison test passes.
6. **Build-system detection exceeds supported configuration.** Build Doctor recognizes CMake, Meson, Autotools, Make, Bazel, and Cargo. Configured project-build plans support CMake and plain Make; unsupported higher-level systems are intentionally refused. This is a material onboarding limitation for general fuzzing engineers, not a defect in refusal behavior.
7. **Kernel and platform support are asymmetric.** Kernel triage parses and deduplicates retained syzkaller evidence without userspace reproduction or minimization. Patch-to-Proof excludes syzkaller and is unavailable on Windows. These capabilities must not inherit userspace support claims merely because all four engine adapters exist.
8. **Some documentation claims exceeded retained evidence (corrected).** Getting Started says every finding is a reproduced real crash. Kernel triage explicitly performs no reproduction, and the product retains inconclusive findings. The same guide names a 0.1.0 installer while the product is 0.4.0. The release checklist lists ten common gates while `gates.sh` currently defines thirteen. Corrected the finding explanation, generalized the installer version, made the release checklist refer to the canonical gate list, and replaced the example guide's missing-promotion sequence with an exact-attempt Work Order walkthrough. Treat guides as executable acceptance material.

9. **A clean regression replay claimed a fix (corrected).** `verify_regressions` returned `no crash on replay (fixed)`, and its behavior test required that wording. A clean current-harness replay omits original reproduction, reviewed patch/build identity, regression corpus and follow-up fuzzing required by Patch-to-Proof. The correction uses observational wording and documents that `RegressionResult.verified` means replay completion only. RED/GREEN evidence is recorded below.

10. **Two established expert workflows need further product work.** Searches of the service, CLI, GUI and designs found no source-revision bisection or regression-range workflow. ClusterFuzz documents regression ranges for reliable crashes and can identify the introducing commit when builds are archived. The reviewed standard userspace run path also does not configure libFuzzer `-jobs`/`-workers`/`-fork` or AFL++ `-M`/`-S` workers: CPU limits alone do not provide intra-target parallel fuzzing. These are source-inspection findings, not measured throughput defects. Evaluate them alongside existing portfolio concurrency before claiming expert workflow parity. [ClusterFuzz triage](https://google.github.io/clusterfuzz/using-clusterfuzz/workflows/triaging-new-crashes/), [libFuzzer parallel execution](https://llvm.org/docs/LibFuzzer.html#parallel-fuzzing).

## Competitive criteria

These are proposed acceptance targets for oxfuzz, not claims about measured performance:

- **First useful harness:** measure engineer active minutes, wall time, model spend, build failures, target-entry evidence and useful corpus growth on pinned C, C++, and Rust projects. Include generated headers, dependencies and duplicate function names.
- **Engine effectiveness:** compare oxfuzz orchestration with the same pinned engine, harness, initial corpus, sanitizer, hardware and budget using multiple independent seeds. Retain coverage-over-time and confirmed unique bugs, not a single lucky crash. FuzzBench provides reproducible benchmarking infrastructure and statistical comparisons. [FuzzBench](https://github.com/google/fuzzbench).
- **Corpus usefulness:** demonstrate coverage-preserving merge and regression-input execution, which are established libFuzzer workflows. Compare AFL reduction quality with native AFL++ tooling rather than treating fewer files alone as success. [libFuzzer documentation](https://llvm.org/docs/LibFuzzer.html), [AFL++ fuzzing workflow](https://aflplus.plus/docs/fuzzing_in_depth/).
- **Finding actionability:** a fresh recipient can identify the exact source/build, reproduce and minimize a crash, inspect its regression range, and assess a patch with explicit inconclusive outcomes. ClusterFuzz's triage workflow is a useful comparator for actionable retained crash information. [ClusterFuzz triage](https://google.github.io/clusterfuzz/using-clusterfuzz/workflows/triaging-new-crashes/).
- **Daily operation:** time yesterday's-finding lookup, external harness qualification, corpus import, comparison setup and interrupted-closeout recovery. Include keyboard-only operation and concurrent runs. Report median/P95 and failure rate; choose final thresholds after collecting a baseline.
- **Overnight reliability:** run a controlled soak with worker loss, Docker restart, disk limits and service restart. Every interrupted run must have a named retained state; no duplicate finding publication or silent lost campaign is acceptable.
